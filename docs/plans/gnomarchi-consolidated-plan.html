Verdict

Port every inventoried Omarchy product feature into a tracked registry row with status native port adapt rebuild or defer. “All features” means none are silently dropped; Hyprland-identical UX is not required under the stock-GNOME decision.

Wiki ADR files under .guild/wiki/decisions/ remain an audit trail. This HTML plan is the planning source of truth; decisions are inlined below so you do not need to open separate records to execute.

Locked decisions (inlined)

D1 — Desktop identity

Stock GNOME, slightly omakase’d. GNOME Shell + Settings/Quick Settings; curated defaults (apps, themes, menu, agents). Not a tiling-first product. PaperWM/Forge optional later only.

D2 — Plugins

Multi-runtime plugin manifest (overlay-app, menu-module, user-service, status-indicator; optional gnome-shell-extension). Separate theme-pack and desktop-app artifacts. Shell extensions last / version-pinned. Same agent loop as Omarchy: skills → artifact → CLI lifecycle → Make something.

D3 — Install order

Overlay on existing Arch first, then ISO that reuses the same install/ stages.

D4 — Packaging

Custom pacman repo for ISO/overlay default path; AUR PKGBUILDs as fallback.

D5 — Public name

gnomarchi everywhere (CLI, packages, git identity). Remote when first overlay is usable.

D6 — Default apps

Ghostty + Neovim + Chromium. GNOME Console/Text Editor/Epiphany installable, not defaults.

D7 — Themes

Prefer vendoring Omarchy theme packs if license/branding allow (attribute; no official claim). Else original Gnomarchi packs inspired by common schemes. Theme engine ships against a minimal original set until the license gate clears.

Parity rule

For each Omarchy feature:

  1. If GNOME already provides it → native (wire menu/hotkey only).
  2. If portable scripts/CLI → port.
  3. If same intent, different API → adapt.
  4. If Quickshell/Hyprland-specific → rebuild on Gnomarchi contracts.
  5. If conflicts with D1 or v1 scope → defer with rationale + revisit trigger (never delete from registry).

Future improvements — mapping path

Omarchy will keep shipping features. Gnomarchi tracks them without guessing:

1. Living registry (source of truth for parity)

Add features/registry.yaml (generated table in docs optional). Each row:

- id: omarchy.shell.plugin-system
  omarchy_refs: ["manual/shell-plugins", "v4.0.0"]
  title: Shell plugin add/clone/validate
  status: rebuild          # native|port|adapt|rebuild|defer
  gnomarchi_path: "plugin/ lifecycle + adapters"
  phase: P3
  defer_reason: null
  last_reviewed: 2026-10-20
  upstream_notes: ""

2. Sync process (every Omarchy release)

  1. Read Omarchy release notes / manual changelog.
  2. Diff against features/registry.yaml ids.
  3. Add rows for new features (status: triage → then assign).
  4. Bump last_reviewed; open plan tasks for port|adapt|rebuild.
  5. Never delete rows; mark defer or wont with reason tied to D1–D7.

3. Agent-assisted sync

Skill gnomarchi-upstream-sync (post-P5): given release notes URL/text, propose registry diffs; human confirms before merge.

4. Improvement backlog buckets

  • Parity gap — Omarchy has it; our status ≠ native/port done.
  • GNOME-native win — we inherit upstream GNOME improvements “for free”; note in registry.
  • D1-blocked — tiling/bar chrome; revisit only if identity decision changes.

Phases

  • P0 — Contracts: manifest, theme schema, state dirs, CLI stubs, seed features/registry.yaml from this matrix
  • P1 — Theme engine + skill + minimal packs (license gate for Omarchy vendoring)
  • P2 — Menu + menu-module runtime
  • P3 — Plugin lifecycle (overlay-app + user-service + validate/clone/add)
  • P4 — Hotkeys, cheatsheet, capture wrappers, Settings deep links
  • P5 — Agents stack, Make something, gnomarchi-app, crash skill
  • P6 — Overlay installer + pacman repo wiring + defaults (Ghostty/nvim/Chromium)
  • P7 — Optional Shell-extension adapter (narrow)
  • P8 — ISO
  • P9 — Marketplace, Windows VM, deferred chrome (bar/tiling/video wallpaper), upstream-sync skill
