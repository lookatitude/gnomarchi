Agentic integrations plan

How Omarchy wires agents, skills, plugins, themes, apps, and the menu — and how Gnomarchi mirrors those concepts on stock GNOME (slightly omakase’d).

Plan Updated 2026-10-20 Q1: stock GNOME Companion to omarchy-to-gnome-comparison

Verdict

D1: Gnomarchi keeps Omarchy’s integration shape (skills → agents → typed artifacts → CLI lifecycle → menu “Make something”), but swaps Quickshell QML plugins for a multi-runtime plugin model that fits GNOME: Shell extensions, status indicators, menu modules, themes, GTK apps, and user services.

The product promise is the same: an agent can create, install, enable, validate, and ship an extension of the desktop without the user learning the plumbing. The runtime is different; the contracts must stay agent-legible.

✓

F1: Omarchy’s power is not QML itself. It is (1) one manifest schema, (2) one CLI for add/clone/enable/validate, (3) skills that teach agents the schema, (4) theme-as-data separate from code-as-plugin, (5) starter prompts that hand the agent a finished brief.

F2 — Theme vs plugin: Themes change colour/token. Plugins change behaviour/structure. Themes cannot install plugins. Gnomarchi must keep this split — it is what makes agent edits safe to auto-apply for themes and gated for plugins.

Shared contracts (agent-legible)

1. Unified plugin manifest

One schema agents always write. Runtime adapters do the GNOME-specific install.

{
  "schemaVersion": 1,
  "id": "io.github.alice.weather",
  "name": "Weather",
  "version": "0.1.0",
  "author": "Alice",
  "license": "MIT",
  "description": "Shows weather in a panel overlay.",
  "kinds": ["overlay-app", "menu-module", "user-service"],
  "entryPoints": {
    "overlayApp": "app/",
    "menuModule": "menu/weather.jsonc",
    "userService": "service/weather.service"
  },
  "requires": {
    "gnomarchi": ">=0.1",
    "commands": ["curl", "jq"]
  },
  "dbus": {
    "name": "org.gnomarchi.plugins.weather",
    "path": "/org/gnomarchi/plugins/weather"
  }
}

2. Theme pack contract

Unchanged from the comparison doc: colors.toml (24 semantic colours) + emitters for GTK, GNOME Shell (User Themes), terminal, nvim, btop, Chromium, agent skins. Theme install never runs plugin code.

3. Menu module contract

Agents extend the omakase menu without forking the UI:

{
  "id": "trigger.weather.refresh",
  "path": ["Trigger", "Weather", "Refresh"],
  "command": "gnomarchi-bus call weather.refresh",
  "keywords": ["weather", "forecast"]
}

4. State directory

~/.local/state/gnomarchi/current/
  theme/           # active theme symlink + generated files
  agent/           # default agent id, usage cache
  plugins.json     # enabled set + placements
~/ .config/gnomarchi/
  plugins/         # third-party + clones

  shell.toml       # machine overrides (fonts, not colours)
/usr/share/gnomarchi/
  plugins/         # first-party

A1: Ship templates next to each skill (templates/): minimal overlay-app, status-indicator, menu-module, user-service, theme pack, GTK app. Agents clone templates; they should not invent project layout.

Skill quality bar (match Omarchy’s experimental honesty)

  • Skills say: prefer plan mode first; expect rollback.
  • Skills forbid editing /usr/share/gnomarchi; only ~/.config and clone dirs.
  • Skills require gnomarchi plugin validate / theme validate before enable.
  • Skills document the trust prompt text the CLI shows on plugin add.

Make something flows

Omarchy’s agents panel offers starter prompts for theme, plugin, and app. Gnomarchi exposes the same three (plus menu module) from Menu → Make and the Agents window.

Flow A — New theme

  1. User: “Make a theme like Tokyo Night but greener.”
  2. Menu launches gnomarchi agent prompt --skill gnomarchi-theme "…".
  3. Agent writes pack under ~/.config/gnomarchi/themes/….
  4. Runs gnomarchi theme validate then gnomarchi theme set.
  5. Theme-changed D-Bus signal updates GTK apps, terminal configs, agent skins.

Flow B — New plugin (typical: overlay-app + menu-module)

  1. Starter: “Build a plugin that shows reminders.”
  2. Skill forces runtime choice: prefer overlay-app + user-service, not Shell extension.
  3. gnomarchi plugin scaffold reminders --kinds overlay-app,user-service,menu-module.
  4. Agent fills templates; validate; enable.
  5. Hotkey / menu entry summon via gnomarchi-bus summon io.github.user.reminders.

Flow C — New desktop app

  1. Starter uses gnomarchi-app.
  2. Scaffold in ~/Work/<name> with git init.
  3. Theme class watches ~/.local/state/gnomarchi/current/theme/colors.toml.
  4. bin/install → local package → appears in GNOME app grid + optional menu Launch entry.

Flow D — Clone and modify first-party

Parity with omarchy plugin clone:

gnomarchi plugin clone gnomarchi.agents --edit
# → ~/.config/gnomarchi/plugins/$USER.agents
# routes IPC id gnomarchi.agents → clone

Cross-tool wiring (the integrations that matter)

W1 — Theme fan-out

gnomarchi theme set is the hub. One command updates:

  • GTK color-scheme + optional CSS
  • GNOME Shell theme (if User Themes enabled)
  • Foot/Ghostty/Kitty config snippets
  • Neovim / btop generated files
  • Chromium theme extension data if present
  • Claude Code / Pi / OpenCode / Hermes skin files
  • Emits org.gnomarchi.Theme.Changed for running GTK apps and plugins

W2 — Agent ↔ desktop

EventIntegration
Pick default agentWrites state; next a / hotkey / menu uses it; mise installs if missing
Theme changeAgent harness theme files rewritten
Process crashuser service watches coredump → notification action → gnomarchi agent crash <pid>
Make somethingPre-baked prompt + skill + cwd ~/Work
Usage refreshTimer updates cache; Agents window reads JSON (no Quickshell required)

W3 — Menu ↔ scripts ↔ plugins

Menu entries never embed logic. They call gnomarchi verbs or plugin D-Bus methods. Agents that add menu modules only add declarations + scripts under the plugin tree.

W4 — Capture / hardware helpers

Screenshot/OCR/QR wrappers remain CLI. Menu Trigger → Capture calls them. Plugins may subscribe to gnomarchi-bus signals (e.g. “screenshot taken”) without owning grim/slurp.

W5 — Install path ↔ skills

On overlay install and ISO first-boot, skills are symlinked once. gnomarchi update refreshes skill content from the package without wiping user-added skills in ~/.agents/skills.

W6 — Stock GNOME surfaces used as hosts

Quick Settings / panel

Stock. Plugins add StatusNotifier icons instead of inventing a bar.

Overview search

Apps from gnomarchi-app appear automatically via .desktop.

Notifications

Actions for crash diagnosis and agent headroom switching.

Settings

Deep-link from menu instead of rebuilding Audio/BT/Network panels.

CLI surface (parity list)

gnomarchi menu [path]                 # open GTK command palette
gnomarchi theme set|list|validate|get
gnomarchi plugin list|add|remove|enable|disable|clone|update|validate|scaffold
gnomarchi app scaffold|install        # desktop app helpers
gnomarchi agent [prompt|crash|account|usage-update|…]
gnomarchi default agent|terminal|editor|browser
gnomarchi update                      # system + skills + plugins git ff
gnomarchi reinstall configs           # rescue after agent mess
gnomarchi-bus summon|hide|toggle|call|rescan

Plugin enable is runtime-aware: extension → gnome-extensions; service → systemd; overlay → desktop+autostart registration; menu-module → symlink into extensions dir + rescan.

Trust and safety (copy Omarchy’s honesty)

  • Themes are data-filtered (colours/tokens only).
  • Plugins are unsandboxed user code. plugin add always confirms; never runs install hooks; never sudo.
  • Validate before enable; refuse reserved gnomarchi.* ids for third parties.
  • No symlinks inside plugin trees (same as Omarchy validate).
  • Clone built-ins instead of editing /usr/share.
  • Document: Shell extensions have higher blast radius than overlay apps; skills bias agents away from them.

Implementation phases (integrations first)

Installability (overlay then ISO) rides on top of these contracts so agents work the day the first image boots.

  • P0 — Contracts: manifest schema, theme schema, state dirs, CLI stubs that validate/list only
  • P1 — Theme engine + gnomarchi-theme skill: set/list/validate + fan-out to GTK/terminal/nvim; agent can create a theme end-to-end
  • P2 — Menu + menu-module runtime: GTK palette; agent can add a Trigger entry via skill
  • P3 — Plugin lifecycle + overlay-app + user-service adapters: add/clone/enable/validate; scaffold templates; gnomarchi-plugin skill
  • P4 — Agents stack: mise wrappers, default agent, Agents GTK window with Make something, crash skill, theme sync to harnesses
  • P5 — gnomarchi-app skill + one reference app (e.g. simple calculator or notes) proving theme live-update
  • P6 — Overlay installer on existing Arch+GNOME: packages, skills symlink, dconf defaults (stock GNOME omakase)
  • P7 — Optional Shell-extension adapter + skill (narrow, version-pinned)
  • P8 — ISO (archiso + offline mirror) wrapping the same overlay stage
  • P9 — Marketplace / discoverability (git topic + validate in CI)
i

D2 — Install order: Build overlay installer before ISO. Omarchy’s own escape hatch is curl | bash on vanilla Arch; ISO is the polished path. Same split: Path A existing system, Path B ISO calling the same install/ stages.

Path A — Existing system (what it takes)
  1. Prereq: Arch (or Arch-based) with working network; prefer already-on GNOME Wayland, or installer installs gnome + GDM.
  2. curl -fsSL …/install | bash or clone repo and run install/overlay.sh.
  3. Stages: keyring/repo (optional) → package list → enable GDM/graphical → dconf omakase dump → symlink skills → enable first-party plugins → first-login Agents invite.
  4. Non-goals for v1: converting Hyprland Omarchy in-place; migrating Quickshell plugins automatically.
  5. Rollback: gnomarchi uninstall overlay removes packages it marked, restores dconf backup.
Path B — ISO (what it takes)
  1. Separate gnomarchi-iso or iso/: fork archiso releng, offline mirror of base + gnomarchi packages (Omarchy pattern).
  2. Live env runs guided installer (disk/LUKS/user) then chroots into the same install/ stages as Path A.
  3. Build via containerized mkarchiso; CI publishes ISO + checksum.
  4. Heavier: GPU firmware choices, dual-boot free-space flow, deferred first-boot — after overlay is proven.

Acceptance tests (agentic promise)

  • Agent with only gnomarchi-theme skill creates a theme; theme set changes GTK + terminal without manual edits
  • Agent scaffolds plugin via template; plugin validate passes; enable makes menu entry and summon work
  • plugin clone of a first-party plugin survives gnomarchi update of the package
  • Make something → app builds, installs, follows theme accent live
  • Crash notification action opens default agent with diagnose skill context
  • Theme switch updates at least one agent harness skin file
  • Overlay install on clean Arch+GNOME reaches Agents invite without Hyprland packages
